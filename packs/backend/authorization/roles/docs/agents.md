## Authorization: by role

- Access by role goes through a policy, never a role check. A module's policies are registered in its Api project's `<Module>Policies : IModulePolicies`, under names its Application project declares in `<Module>PolicyNames`, `<module>.<permission>` (`billing.approve-invoices`), each built with `RequireRole(...)`. `IsInRole`, `ClaimTypes.Role`, `[Authorize(Roles = ...)]`, or `RequireRole` anywhere else fails the architecture rule `OnlyModulePoliciesCheckRoles`.
- To add a permission: add a constant to the module's `<Module>PolicyNames` in Application (`public const string ApproveInvoices = "billing.approve-invoices";`) and a policy to its `<Module>Policies` in Api (`policies.AddPolicy(BillingPolicyNames.ApproveInvoices, policy => policy.RequireRole("accountant"));`), then name it on the endpoint with `.RequireAuthorization(BillingPolicyNames.ApproveInvoices)`. {{ add_role_rule }}
- An endpoint names only its own module's policies; `EveryEndpointPolicyIsRegisteredByItsModule` fails for one its module does not register or another module registers too.
- Every new endpoint that requires a policy gets an integration test with a user who holds it (200 or what it returns), one who does not (403) and no token (401), like `<Module>RoleTests`.
- Local users: `developer` / `developer` holds the {{ role_kind }} `manager` (as does `developer-b` with tenancy); `visitor` / `visitor` has no roles. Each module's sample policy `<module>.manage` requires `manager`{{ if claims }} and `department=finance`{{ end }}; `GET /<module>/permissions/manage` answers 200 with a `PermissionDto` for a holder and 403 for anyone else signed in. It is an ordinary endpoint: the `CanManage` query through the dispatcher, in the OpenAPI document, asked by the module's page through the generated client; never `ExcludeFromDescription` it.
