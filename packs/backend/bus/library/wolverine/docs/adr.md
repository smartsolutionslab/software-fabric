# Messaging library: Wolverine

**Status:** Accepted (generated)

## Decision

Wolverine (MIT) carries integration events. Each module's unit of work is Wolverine's EF Core outbox over the module's DbContext: queued events are stored in the same transaction as the module's changes and sent after commit; incoming messages go through a durable inbox. Envelopes are kept in the `wolverine` schema of the project's database.

{{ if project["backend.bus.transport"] == "kafka" }}Over Kafka every integration event has a topic named after its full type name (`{{ namespace }}.Contracts.Billing.InvoicePaidV1`); the host publishes each event to its topic and listens, as one consumer group named after the project, to the topics of the events its modules consume.{{ if project["backend.topology"] == "services" }} With `backend.topology: services` each service host listens as a consumer group of its own, named after its module, which the AppHost passes it as `Messaging:ConsumerGroup` (a service host started without it fails at startup): services sharing one group would split each topic between them, and an event would reach only one of the services that consume it.{{ end }}

{{ end }}{{ if project["backend.bus.transport"] == "rabbitmq" || project["backend.bus.transport"] == "azure-service-bus" }}An integration event that one module publishes and another module of the same host consumes does not cross the broker: Wolverine routes a message it has a consumer for to a durable local queue in the host (`local://<namespace>.contracts.<module>.<event>/` in the host log, in lower case), and consults the broker's routing only for a message no module of the host consumes. The host's local queues are durable (`UseDurableLocalQueues()` in `src/Host/Wiring/Messaging.cs`): such an event is stored with the publishing module's changes, in the same transaction, and stays in the inbox (`wolverine.wolverine_incoming_envelopes`) until its consumer succeeds, so a host that stops meanwhile delivers it after a restart. It is retried and dead-lettered as below, exactly as one from the broker. The broker carries only what another service sends or receives: the host publishes an event none of its modules consume to {{ if project["backend.bus.transport"] == "rabbitmq" }}an exchange and queue{{ else }}a queue, created at startup through the management API,{{ end }} named after its full type name, and listens to the queue of each event its modules consume, where another service's events arrive. This is intended: modules of one host are not worth a broker hop per event, and the outbox and inbox keep the local queue durable.

{{ end }}{{ if project["backend.mediator"] == "wolverine" }}Wolverine discovers consumers (`*Consumer`) in the modules' Application projects, and their command and query handlers, which the project's mediator invokes on Wolverine's bus (see the mediator's ADR).{{ else }}Wolverine discovers only consumers (`*Consumer`) in the modules' Application projects. Commands and queries stay with the project's own mediator; Wolverine is not used as a second one.{{ end }}

A consumer that throws is retried with backoff before its message is given up, as the in-process outbox does: the retries come 1, 2, 4, 8, 16 and 32 seconds after the failure before them, seven attempts within about a minute. Each retry is scheduled in the durable inbox rather than waited for in memory, so it survives a restart and the listener goes on delivering other messages. A message whose seventh attempt fails moves to `wolverine.wolverine_dead_letters` with its exception; setting `replayable = true` on its row delivers it again.{{ if project["backend.bus.transport"] == "rabbitmq" || project["backend.bus.transport"] == "azure-service-bus" }} That holds for a message the host received from the broker too: Wolverine's {{ if project["backend.bus.transport"] == "rabbitmq" }}RabbitMQ{{ else }}Azure Service Bus{{ end }} transport would move it to a dead-letter queue on the broker (`wolverine-dead-letter-queue`) instead, which the host turns off, so a developer looks in one place.{{ end }} A minute rides out a database restart, a failover or a broker reconnect; a failure that outlasts it is no longer transient and belongs in front of a developer. The outbox, which keeps a failed message in the module's own table, tries ten times over about eight and a half minutes; Wolverine stops sooner because its dead letters are the place a developer looks, and replays from.

Wolverine generates handler code at startup (`WolverineFx.RuntimeCompilation`). Production deployments should pre-generate it with `dotnet run --project src/Host -- codegen write` and static type loading; wiring that into the release build is open.

## Consequences

- No event is lost when the broker is down: it waits in the outbox.{{ if project["backend.bus.transport"] == "rabbitmq" || project["backend.bus.transport"] == "azure-service-bus" }} Events between modules of the host do not wait: they never reach the broker.
- An event a module of the host consumes is not sent to the broker at all, so another service never receives it. Letting a service consume it too, or moving a module to a host of its own, changes the routing in `src/Host/Wiring/Messaging.cs`.{{ end }}
- Delivery is at least once, and a failed consumer runs again: consumers must be idempotent.
- A consumer that fails for good is dead-lettered after about a minute, not at once.
