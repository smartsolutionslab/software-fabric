## Message transport: none (in-process outbox)

- There is no broker. Publish integration events through `I<Module>UnitOfWork` exactly as with one: `PublishAsync(...)`, then `CommitAsync(...)`. The events are saved with the changes in the module's `outbox_messages` table and delivered in-process after the commit. The unit of work opens that transaction itself: `CommitAsync` refuses to run inside one you began on the module's DbContext.
- A consumer is a public class `<Event>Consumer` in a module's Application project with a public, non-generic `Handle(<Event> message)` returning `void` or `Task`, never `async void`; one that awaits is `async Task HandleAsync(<Event> message)` (async methods end in `Async`). `<Event>` is the sealed event record itself: an event is delivered only to handlers of exactly its type, never to a handler of a base type or interface. Further `Handle`/`HandleAsync` parameters may be a `CancellationToken` or services; constructor dependencies are injected too. The architecture rule uses the dispatcher's own definition (`IntegrationEventConsumers.Problem`), so what it accepts is what gets delivered.
- Do not call another module's code or consumer directly, and do not add a broker, a messaging library or a background queue by hand: the transport is a project choice.
- The MigrationRunner creates each module's outbox table; do not map it in a DbContext, add it to a migration, or create it from the host. A test that uses a unit of work runs the MigrationRunner first.
