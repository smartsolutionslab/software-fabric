# Tenancy: a schema per tenant

**Status:** Accepted (generated)

## Decision

All tenants share the database, and each tenant has a schema of its own per module: `<module>_<tenant>`, such as `billing_tenant_a`, with its own migrations history table. The tables carry no tenant column, and the domain model never sees a tenant. A module's DbContext works in the schema of the current tenant: EF Core caches one model per module and schema, and the migrations `dotnet ef` writes for the module's schema are moved to the tenant's when they run. Once a context's whole model is configured, its own `OnModelCreating` included, before or after the base's, a default schema or a table or view that still names the module's schema moves to the tenant's too.

The tenants are a list, `Tenancy:Tenants`, which the AppHost sets on the MigrationRunner and on the host (`tenant-a` and `tenant-b` locally, the groups the identity provider's local users belong to). The MigrationRunner first checks every module, then migrates every module in its own schema, which checks each model against its snapshot, then creates and migrates every module's schema for each listed tenant. The host never creates a schema and never migrates: it needs no rights to change the database's structure, and several instances never race to migrate a tenant.

The current tenant comes from the user's token: {{ tenant_claim_adr }}. Work outside a request — consumers, jobs — sets the tenant explicitly with `TenantScope.Begin(tenantId)`. A module's DbContext picks its schema at its first query or save, not when it is created, so a consumer's injected context, created before `Handle` begins the scope, works in that tenant's schema; a context first used before the scope keeps the module's own. A tenant that is not listed, or no tenant at all, works in the module's own schema, which holds no rows: every query there finds nothing, and saving fails.

## Consequences

- A tenant's rows cannot be read by another tenant's query: they are in another schema, not behind a filter.
- Adding a tenant means adding it to `Tenancy:Tenants` in the AppHost and running the MigrationRunner again; a tenant the token names but the list does not sees nothing until then. A tenant name is lower-case letters and digits joined by hyphens; any other name in the list fails the runner and the host. So does a tenant whose schema would be longer than the 63 characters PostgreSQL keeps, and the runner fails before migrating any tenant when two module and tenant pairs, or a pair and another module, would share a schema name (module `billing` with tenant `a-b` and module `billing-a` with tenant `b` are both `billing_a_b`). A module whose own schema ends like a listed tenant's (`billing_a`, with tenant `a` listed) fails as soon as its context is created, before its own migrations run.
- Every migration runs once per tenant, so a migration's time grows with the number of tenants. Raw SQL in a migration (`migrationBuilder.Sql`) runs as written, in whatever schema it names, so it must not name the module's schema.
- Reading across tenants means opening each tenant's schema in turn; there is no query over all of them, and no `AcrossTenants()` as a tenant column with roles has (the repository owner's decision, 2026-11-12). There, staff read across tenants by lifting one query filter; here a tenant's rows are in another schema, so reading them all is a different design (a query per schema, or a view over them), not a filter to lift. A database per tenant (no pack yet) has none either, for the same reason one step further: the rows are in another database, which one connection cannot query at all.
- There are no records shared by all tenants, as a tenant column with roles has with `SharedByAllTenants()` and `WritesSharedRecords()` (the repository owner's decisions on #623, 2026-11-12). There a shared type simply has no tenant filter; here a shared type would need a schema that does not move with the tenant, while this pack moves every table that names the module's schema to the tenant's and keeps the module's own schema empty, so it is a different design. A database per tenant (no pack yet) has none either, one step further: shared records would need a database outside every tenant's, reached by a second connection.
- **Refused, not moved** (owner decisions on #253): a module that uses any of these fails with an error naming each one, when `dotnet ef` builds its model and in the MigrationRunner before any module migrates, in any schema, so nothing is shared between tenants silently:
  - seed data through `HasData` (one migration would insert it into every tenant's schema);
  - entity splitting, `SplitToTable` or `SplitToView` (a fragment's table keeps the schema it names, so tenants would share it);
  - a reference to the module's schema in SQL, as an identifier qualifying an object, quoted or not, with whitespace or comments before its period (`nextval('"billing"."ids"'::regclass)`, `billing.mood`, `billing /* c */ . shared_value()`), in the model's default or computed SQL, a check constraint, an index's filter, a column type, a migration, or in a provider's annotation, such as `HasPostgresEnum("billing", "mood", ...)`'s `Npgsql:Enum:billing.mood`. The model is checked once all of it is configured, a context's own `OnModelCreating` included. A comment names nothing, and neither does a string literal unless it is an object's name, cast to an object identifier type, qualified or not (`'"billing"."ids"'::regclass`, `CAST('billing.ids' AS pg_catalog.regclass)`), or given to a function that takes one (`nextval('billing.ids')`): `'billing.example'` is a value, not a reference. A literal value is data, not SQL: a default value (`HasDefaultValue("billing.example")`) or a comment is never read as a reference;
  - sequences, explicit (`HasSequence`) or HiLo's (`UseHiLo`).
  Before migrating any module, the MigrationRunner checks every module: the listed tenants' names, that no two module and tenant pairs share a schema, that each model builds and matches its snapshot, and that each migration can be moved. One module that fails leaves every module unmigrated. Lifting any of these is its own change.
