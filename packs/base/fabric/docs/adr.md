# Board protocol

**Status:** Accepted (generated)

## Decision

Agents coordinate through GitHub, never with each other, so any runtime that can run `gh` takes part: Claude Code in the cloud or locally, Codex, GitHub Actions. The protocol is the scripts in `.github/scripts/board/`, one per step: `next.sh` claims, `release.sh` gives back, `escalate.sh` hands to a developer, `janitor.sh` (hourly) and `return-to-todo.sh` (on unassignment) return issues to Todo.

- **Eligibility** is labels: `agent:ready`, `lane:<lane>`, none of `agent:blocked`, `agent:claimed` or `needs:*`, no assignee. A human assignee always wins; an escalation no owner had capacity for has no assignee and is held by its `needs:*` label. `agent:claimed` is set on a claim and removed when the claim is released, escalated or lapses, so a claimed issue looks taken without a board; it is a pre-filter, and the branch stays the lock.
- **The branch is the lock**, and it moves only by `git push`. A claim is an empty commit `chore(board): claim #<issue>` pushed to `agent/<issue>`, a name nothing can change (a title in it would let two agents push two locks for one issue); a released, escalated or lapsed claim gets `chore(board): release #<issue>` on top, which parks the branch with its work for the next agent; resuming pushes a new claim commit on top of that. Each step builds on the commit it saw, so a push that finds the branch moved is not a fast-forward and is rejected: of two agents, one wins. No branch is ever force-pushed, renamed or deleted, which cloud sessions refuse.
- **Lease.** A claim lapses when the branch's last commit (the claim is one) is older than `BOARD_LEASE_HOURS` (2 h by default) and it has no open pull request.
- **Escalation** labels the issue (`needs:human`, `needs:decision`, `agent:blocked`), assigns the owner of its lane with the fewest open assignments below the WIP limit (`docs/owners.yml`), and says why in a comment.
- **Board fields.** When `.github/board.env` names a GitHub Project, the scripts keep its `Status` (Todo, Claimed, In Progress, In Review, Blocked, Done) and `Executor` fields current; without one, labels and comments carry the protocol alone.
- **Review across model families.** Every agent commit carries `Agent-Executor: <family>-<runtime>/<detail>`; the review workflow has the other family review the pull request. A pull request with commits from both families has no independent reviewer and fails that check.
- **Conventional Commits.** Every commit a pull request adds, merges aside, is `<type>(<scope>)!: <subject>` with a header of at most 120 characters; the board's own commits (`chore(board): claim #<issue>`) are too. Scopes come from the project, not from a list kept per module: its modules in `fabric.yaml`, which `fabric add-module` extends, and the fixed ones in `.github/commit-scopes`. `check-commits.sh` needs git alone, so the check costs a backend-only project no Node toolchain. It checks a pull request's own commits only: history already on the default branch is never rewritten.
- **Findings are a gate.** The reviewer answers in the shape of `.github/review-findings.schema.json` (severity blocking or optional, file, line, message). `report-review.sh` posts them as a pull request review, on their lines where GitHub accepts that, and fails the check when one blocks or when the reviewer reported no findings list at all.

## Consequences

- No dispatcher to keep alive: the state is on GitHub. A crashed agent costs one lease, not a stuck issue.
- The scripts call GitHub's REST API only (`gh api`) and move branches with `git push`: Claude Code's cloud sessions refuse GraphQL, which `gh issue`, `gh pr` and `gh repo` use, and branch writes through the API. The board fields are the exception, since GitHub Projects have no REST API: in such a session the scripts run on labels and comments alone.
- Workflows changing the board need a token with the `project` scope (`BOARD_TOKEN`); the default token can change labels, branches and comments only.
- The reviewer is GitHub Copilot CLI (`copilot -p`, at the exact version `REVIEWER_CLI_VERSION` in `cross-model-review.yml`), on the reviewing family's model: `REVIEW_MODEL_CODEX` (a GPT model) for a change Claude wrote, `REVIEW_MODEL_CLAUDE` for one Codex wrote. Both are set at the top of that workflow and nowhere else; change them there when Copilot offers newer models. A model the account lacks makes the review fail, not pass.
- The review signs in with the repository secret `COPILOT_GITHUB_TOKEN`: a fine-grained personal access token of an account licensed for Copilot (an organisation's own token is refused where Copilot is licensed to a person, not the organisation). Create it under Settings → Developer settings → Fine-grained tokens with the account permission **Copilot Requests** and nothing else, give it an expiry (it then has to be renewed, or reviews fail), and store it under Settings → Secrets and variables → Actions. A missing or empty secret fails the review naming it; it never passes. Every review is one prompt, and counts against that account's Copilot premium requests, at the multiplier of the model it uses. The reviewer reads the pull request's checkout in an untrusted folder and without its custom instructions: its rules are the base branch's AGENTS.md and briefs, named in the prompt. Since the diff is untrusted and the step holds the token, the reviewer may run only `git diff`, `git show`, `git log`, `ls` and `grep` besides reading files in the checkout; in prompt mode everything else (writes, other commands, any URL, paths outside the checkout) is refused, and its shell gets no token (`--secret-env-vars`). A reviewer that needs another command gets it here, with a reason.
- The review gate is only as strong as the branch protection around it. The workflow runs the board scripts, the findings schema and the reviewer briefs from the base branch, but the workflow file itself comes from the pull request. Give `.github/` a code owner and protect the default branch: require the code owner's review and the review check.
