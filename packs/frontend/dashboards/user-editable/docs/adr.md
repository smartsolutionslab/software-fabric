# Dashboards: user-editable

## Context

Users want to arrange the figures they watch on dashboards of their own. A dashboard that could name any query would get around every endpoint's authorization, and a saved dashboard is state that needs a home following the same module, tenancy and retry rules as everything else.

## Decision

- **A `dashboards` module stores them** ({{ if module_defaults["module.style"] == "crud" }}CRUD, logical CQRS{{ else }}logical CQRS, and the project's module style like any other module: {{ module_defaults["module.style"] }}{{ end }}).{{ if module_defaults["module.style"] == "ddd" }} A dashboard is an aggregate root, `Dashboard : AggregateRoot<DashboardId>`, changed only by `Dashboard.Create` and `Rearrange`, which keep its rules (name, number of widgets, keys, grid) and answer a broken one with a `DomainError`; the use cases commit through `IDashboardsUnitOfWork`.{{ end }}{{ if module_defaults["module.style"] == "event-sourced" }} A dashboard is an event-sourced aggregate, `Dashboard : EventSourcedAggregate<DashboardId>`, changed only by `Dashboard.Create`, `Rearrange` and `Remove`, which keep its rules (name, number of widgets, keys, grid) and raise `DashboardCreated`, `DashboardRearranged` and `DashboardRemoved`; its stream is loaded and saved through `IDashboardsAggregateStore`. Pages of dashboards and the widget-count chart read the `dashboards` table, a read model the save and remove use cases write right after they save the dashboard's events and commit through `IDashboardsUnitOfWork`; one dashboard is read from its stream. The two writes are not in one transaction: a crash between them, or two requests for one dashboard whose writes interleave, leaves a dashboard missing from, outdated in or left over in the list until its owner next saves it.{{ end }} A dashboard row holds its owner (the token's `sub`, through `ICurrentUser`), its name and its widgets as one JSON column; each widget names a declared widget, a visual (`bar`, `line`, `pie` or `table`) and its place on a 12-column grid. Every read filters by owner{{ if project["backend.tenancy"] != "none" }}, and by tenant through the persistence layer{{ end }}.
- **Writes are idempotent.** The client chooses the id; `PUT /dashboards/{id}` creates or replaces and `DELETE /dashboards/{id}` removes, so a retried request applies once. Another user's id is not found for the caller, and {{ if module_defaults["module.style"] == "event-sourced" }}saving it answers 409 (`dashboards.already-exists`), since the dashboard's stream keeps its owner even after it is removed{{ else }}inserting it fails on the primary key (409){{ end }}: no one replaces someone else's dashboard.{{ if module_defaults["module.style"] != "crud" }} The owner may save a removed dashboard's id again.{{ end }} `GET /dashboards` is paged; `GET /dashboards/{id}` reads one.
- **Widgets are declared, typed, per module.** A module's `IModuleWidgets` (Application project) lists each widget with its key, title and how to build its query; a chart's query answers `ChartSeries`, a table's `PagedResult<TRow>`, and the compiler checks it. Its id is `<module>.<key>`. The query takes nothing but the page, so no caller chooses its input.
- **Nothing else is reachable.** `GET /dashboards/widgets` lists the declared widgets{{ if policies }} whose policy the caller holds{{ end }}, `GET /dashboards/widget-declarations/{id}` describes one of those, `GET /dashboards/widgets/{id}` runs one through the dispatcher as the caller, and saving a dashboard naming any other is refused with `dashboards.unknown-widget`.{{ if policies }} A widget carries its module's policy because it bypasses the endpoint that would otherwise check it.{{ end }}
- **One definition of a valid widget**, `WidgetCatalog.Scan`: a query of the declaring module's Application project with exactly one handler, ids unique{{ if policies }}, a named policy registered by that module{{ end }}. The host refuses to start on a problem; the architecture rule `EveryWidgetIsADeclaredModuleQuery` fails the build on the same ones and on an `IModuleWidgets` outside an Application project.

## Consequences

- A module offers a widget by changing its own Application project; no shared file lists widgets.
- The rule sees that a widget is declared, not that its query reads only what its viewers may see; that stays the query's business, as for an endpoint.
