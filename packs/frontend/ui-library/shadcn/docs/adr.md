# UI components: shadcn/ui

**Status:** Accepted (generated)

## Decision

Components are shadcn/ui: Radix primitives styled with Tailwind, copied into `src/components/ui/` and owned by the project. Add one with `pnpm dlx shadcn@latest add <component>` in `web/app`; `components.json` configures where it lands. The theme for `components.json`'s base colour (slate), in the colour scheme `fabric.yaml` records (`frontend.color-scheme`), lives in `src/index.css`: CSS variables mapped into Tailwind with `@theme inline`, plus `tw-animate-css` for the components' animations. The theme also sets the font `fabric.yaml` records (`frontend.font`) as `font-sans` and `font-mono`, a type scale of `text-display`, `text-title` (a page's `h1`), `text-body` and `text-caption`, and tabular figures in tables and grids, so the digits of amounts line up. The button is the registry's new-york-v4 button (variants default, destructive, outline, secondary, ghost, link; sizes default, sm, lg, icon), so components the CLI adds on top of it type-check. Every list has a loading and an empty state from the project's own components: the registry's skeleton (`src/components/ui/skeleton.tsx`, in the accent colour), and `src/components/ui/empty-state.tsx`, an icon screen readers skip, one sentence and the primary action. No other component library.{{ if project["frontend.architecture"] == "spa" && (project["frontend.routing"] == "react-router" || project["frontend.routing"] == "tanstack-router") }}

The app shell is the registry's collapsible sidebar (`src/components/ui/sidebar.tsx`, with the sheet, tooltip, separator, input and skeleton it uses): the start page and each module's page from the routes the modules register, the theme toggle and (with oidc-client-ts) the user menu in its footer, and above the page the breadcrumbs and a command palette (`cmdk`, Ctrl+K or Cmd+K) that goes to any page by keyboard alone. Toasts are `sonner` in the theme's popover colours; `src/lib/notify.tsx` puts a mutation's success in one as a status message and a failure as an alert, so a screen reader announces them as such (sonner's own list is only a polite live region). Adaptations of the registry: the sidebar's inset is a `div`, since every page renders its own `<main>`; the mobile check reads `matchMedia` only where the browser has it; the command dialog's title labels its search box; the current breadcrumb is text, not a disabled link, so a page's name is one link (the sidebar's); and the menu skeleton has a fixed width, since React's rules want a render without side effects. The shell has its own tests, with axe in both themes, beside it in `src/shell/`.{{ end }}

The theme has two palettes of the same variables, shadcn's slate in the colour scheme: `:root` is the light one and `.dark` the dark one, each swapped as a whole. The app follows the system's `prefers-color-scheme` until the user chooses light, dark or system with the theme toggle in its navigation (`src/theme/`); the choice is remembered in `localStorage` (a blocked storage only forgets it), and a script in `index.html` sets `.dark` on `<html>` before the first paint, so a dark page never flashes light. jsdom computes no colours, so axe in the component tests cannot judge contrast: `src/theme/contrast.test.ts` checks every text colour the components put on a background against WCAG AA (4.5:1) in both palettes, and with the accessibility tests each screen's axe check runs in both themes for what else differs.
{{~ if project["frontend.design-system"] == "tokens-and-components" || project["frontend.design-system"] == "tokens" || project["frontend.design-system"] == "web-components" ~}}

The design system's tokens are imported after the theme, so a colour or radius they define (`primary`, `accent`, `border`, `rounded-md`, …) is theirs; the theme supplies the rest (`card`, `muted`, `destructive`, …). They define no font and no text size, so the theme's font and type scale apply with them too: the typeface is the project's choice in `fabric.yaml`, and a font token would be a second place to make it. Each colour token has a dark value too (`web/packages/tokens/dark/`, compiled under `.dark`), so the dark theme takes the tokens' dark colours, and the contrast test reads the tokens as built over the palettes.
