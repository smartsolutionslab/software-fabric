# Module style: domain-driven design

**Status:** Accepted (generated)

## Decision

Modules model their business with aggregates, entities and domain events. Aggregates derive from `AggregateRoot<TId>`, entities from `Entity<TId>`; both live in the module's Domain project, which depends on nothing but the BCL and `src/BuildingBlocks.Domain`. Invariants are enforced inside the aggregate; nothing outside changes its state except through its methods.

**Domain events are dispatched in-process, after the commit.** An aggregate records what happened with `Raise(...)`. Every module DbContext has a `DomainEventDispatch` interceptor (`src/BuildingBlocks/DomainEvents/`) that collects the events of its tracked aggregates when they are saved and hands each to the module's `IDomainEventReaction<TEvent>` implementations, discovered in its Application project like command handlers. They are reactions, not handlers: a handler answers a command or query (and, with result values, returns a `Result`), while a reaction follows something that already happened and has nothing to return:

- **When.** Right after `SaveChangesAsync` succeeds. Inside a transaction the context began (`Database.BeginTransactionAsync`, which is what the unit of work does), the events wait for that transaction's `CommitAsync`. A rollback, a failed commit, or a transaction disposed without a commit delivers none of them: an event is delivered only for changes that are in the database.
- **Where.** Each reaction runs in a DI scope of its own, created for it, after the caller's changes are committed. It gets its own DbContext: it may load and change aggregates and save them, and the events that raises are dispatched after its save in turn. It does not see the caller's tracked, uncommitted objects, and it is not part of the caller's transaction, which is already committed.
- **A reaction that throws** does not undo the caller's changes and does not reach the caller: it is logged at Error with the reaction and the event, the event's other reactions and the later events still run, and the caller's `SaveChangesAsync` or `CommitAsync` returns normally. Throwing would tell the caller its save failed when it is committed, and would skip what the caller does after the commit (the unit of work accepting its changes and clearing its queued integration events, Wolverine flushing its outbox). Nothing retries a failed reaction: delivery is at most once and in memory, so work that must not be lost, or that another module needs, belongs on an integration event through the outbox. A save canceled after its commit logs the events it did not deliver.
- **Refused saves.** A save with pending events fails before anything is written when the dispatcher could not tell whether, or when, its changes commit: a synchronous `SaveChanges` or `Commit` (reactions are asynchronous), an ambient `TransactionScope`, a transaction the context did not begin (`UseTransaction`), a transaction with savepoints the application created, or a context created without the application's services or logging.
- **Kept or cleared.** A save that accepts its changes (the default) takes the events off the aggregates with them. A save with `acceptAllChangesOnSuccess: false` inside a transaction leaves them on the aggregate until the commit, so a retry after a rollback saves the changes and their events again.

**Every domain event has a reaction or says why not.** `DomainEventReactions` defines once what a reaction the dispatcher delivers to is: a class in an Application project, not generic, with a public constructor, handling a sealed, non-generic event. Discovery registers only those, and the architecture rule `EveryDomainEventHasAReaction` uses the same definition: it fails every reaction that is not one, every event in a Domain project that is not sealed or has no such reaction unless it is marked `[DeliberatelyUnhandled("why")]`, and every marked event that is handled after all.

## Consequences

- Persistence, HTTP and messaging never leak into the Domain project; an architecture rule fails the build if they do. With result values, that includes errors: a Domain error is a `DomainError` (code and message), and only the Application gives it an HTTP status.
- Each aggregate is loaded and saved as a whole; cross-aggregate consistency within a module is eventual, through domain events whose reactions run after the commit.
- An event is delivered only from an aggregate the context tracks when it saves. An aggregate that raised an event but was never added or loaded into the context delivers nothing.
- What the architecture rule cannot see: whether a reaction's constructor dependencies are registered (it fails at delivery, after the commit, and is logged), whether the reaction does what its event needs, and whether an event is actually raised anywhere. It checks the types, not the runtime.
- One open edge of `acceptAllChangesOnSuccess: false`: an aggregate that raised an event but has no changed column counts as accepted, so after a rollback its event is not saved again by a retry.
- Event-sourced modules persist their events in the event store and do not use this dispatcher; their aggregates are not `AggregateRoot<TId>`, so it ignores them.
